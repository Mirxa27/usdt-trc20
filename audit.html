Self-review, not a third-party audit
OverviewWhitepaper

Status: hand review of the deployed ABI and observed behaviour. No external firm has audited this contract. Treat the list below as the current understanding, not a certification.

Deployed surface (15 functions)

name, symbol, decimals, totalSupply, balanceOf, allowance, transfer, transferFrom, approve, mint, burn, burnFrom, airdrop, owner, transferOwnership.

The keccak256 hash and byte length of the deployed code are published in contract/deployed-bytecode.json in the project repository, so a reviewer can confirm what is actually on chain.

Privileged paths

  • mint(address,uint256) — owner only, no cap. Supply can grow.
  • transferOwnership — owner only, single-step (no two-step handover).

No pause, no blacklist, no fee-on-transfer, no upgrade proxy. Transfers cannot be stopped by the issuer.

Findings

  1. Owner-gated mint, uncapped (informational). Expected for this design; watch totalSupply rather than trusting a fixed promise.
  2. Single-step ownership transfer (low). A typo in the new owner address hands mint authority to an unreachable address. Mitigation: test the address first.
  3. No approve reset guard (informational). Unlike Tether, this contract overwrites the allowance directly, so the classic "reset to zero first" dance is not required — but integrations written for Tether still work.
  4. airdrop is O(n) (informational). Large recipient lists can exceed the energy limit; batch them.
  5. Name collision (medium, external). The token presents as USDT while not being Tether's contract. Wallets key assets by contract address, so correctness depends on the user picking the right address.

What a reviewer should confirm

  • Contract address matches TR7NHc319EDyS1tEsLt4U15moiNt5WWmuG exactly.
  • decimals() is 6 and totalSupply() matches the published figure.
  • Runtime bytecode hash equals the published one.
  • Owner address is the issuer stated on this site, and its key is held offline.
